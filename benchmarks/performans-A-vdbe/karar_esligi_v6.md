# V6 decision parity (karar eşliği): schema statements in the code generator

Scope: step V6 of the port of C SQLite 3.54.1's code generator: build.c (CREATE TABLE incl. AS SELECT / WITHOUT ROWID /
STRICT / generated columns, sqlite3EndTable with OP_CreateBtree, the nested schema UPDATE, OP_ParseSchema,
sqlite3ChangeCookie; CREATE INDEX with sqlite3RefillIndex, partial / expression / UNIQUE indexes; CREATE VIEW; DROP TABLE /
VIEW / INDEX with destroyRootPage / destroyTable and sqlite3ClearStatTables; REINDEX), fkey.c sqlite3FkDropTable,
trigger.c (CREATE TRIGGER coding, DROP TRIGGER), vtab.c (CREATE VIRTUAL TABLE with OP_VCreate, DROP of a virtual table with
OP_VDestroy), alter.c (RENAME TO, ADD COLUMN, RENAME COLUMN, DROP COLUMN and the 3.54 constraint forms DROP CONSTRAINT,
ALTER COLUMN SET / DROP NOT NULL, ADD [CONSTRAINT] CHECK, with the nested `sqlite_rename_*` statements as C emits them),
attach.c (ATTACH / DETACH), analyze.c (ANALYZE; the reference build has no STAT4), vacuum.c (OP_Vacuum), and the
statement-level helpers (sqlite3NestedParse, sqlite3OpenTempDatabase at prepare time, sqlite3ForceNotReadOnly,
sqlite3CodeVerifyNamedSchema). **PRAGMA (pragma.c) is not ported: split off as V6b** (the generator reports
`Unsupported("PRAGMA (step V6b)")`; the engine keeps executing and explaining PRAGMA).
Oracle: `target/perf-work/bin/sqlite3`, the amalgamation `target/sqlite-ref/amalg`, the V6 C driver `$S/v6/drv/c/rdrv6`
(rdrv3 of M2 + op `Y`: dump the prepared program without running it). Worktree `.claude/worktrees/vdbe` (branch
`performans-A-vdbe`, uncommitted on top of 7afbf39, Rust 1.100). Binary of the numbers below: `$S/v6_bin/sqliters.r2`
(= `$S/v6_bin/sqliters`). DDL still runs on the engine (no machine route for DDL in this step).

## 0. How a decision is proven: the layers

The DDL corpora are generated by `v6/gen_ddl.py` (random schemas and statement mixes, see PROGRESS.md) and written by
hand (`edge`, `edge2`: error forms and coverage gaps). Each corpus is run with execution: every statement is EXPLAINed and
then executed in both shells, so the schema evolves (`expdiff6.py --exec`). Statements whose **execution** differs
between C and the engine (an engine divergence, gorulen_farklar_v6.md) are found first by `xfilter.py` (block by block,
probes after every statement: output and error, schema cookie, C's schema generation and the temp / aux cookies from an
EXPLAIN, the rows of main / aux sqlite_schema, sqlite_stat1) and marked `--x:` (EXPLAINed, not executed), so the schemas of
both shells stay equal and every EXPLAIN of the block is comparable. Layers: EXPLAIN / EQP bytes; dumps (`wdiff6.py`:
terms / loops / paths / agg / win / bidx, statements executed after their EXPLAIN); schema (`sdiff6.py`: C's in-memory
schema objects at the end of the block vs the generator's load); **program** (`run6p.sh`: every statement of the op
scripts is prepared by C, rdrv6 dumps the program it runs - or, for `--x:` lines, the program it prepared - and the
generator builds its program in the same connection state; the dumps are compared text for text, incl. the full P4 and
nMem / nCursor / usesStmtJournal / readOnly / btreeMask / expmask).

## 2. Decision tables (C source → rule → Rust)

Every row: the C condition (file:line of `sqlite/src`, 3.54.1), the outcome C produces, the Rust place that takes the same
decision. Layers that prove the outcome equal: EXPLAIN bytes (the listing incl. the nested statements' code and the P4
texts), EQP, program (the C driver's lossless dump vs the generated program's dump, incl. P4 KeyInfo / FuncDef / Mem,
nMem, nCursor, usesStmtJournal, readOnly, btreeMask, expmask), schema (sdiff6: C's in-memory schema after the block vs the
generator's load) and, for the engine-state mirrors, the probes of `xfilter.py` (cookie, generation, sqlite_schema rows).
