# Step H1 — decision parity of delete-side B-tree rebalancing (C SQLite 3.54.1 vs sqliters)

Generated by `target/perf-work/h1/fill_karar.py` from the decision-trace run in `tr_final5/`. C line numbers refer to `sqlite/src/btree.c` (3.54.1); Rust locations to `crates/sqliters-btree/src/balance.rs` (B) and `lib.rs` (L).

## 0. Method

* **C side**: instrumented copy of the amalgamation (`h1/ctrace/`, `patch_extra.py` on top of the step-5g `patch.py`; `sqlite/` and `target/sqlite-ref/` untouched). Trace class `bal`; every event carries `ctx=del` (inside `sqlite3BtreeDelete`) or `ctx=ins` (inside `sqlite3BtreeInsert`).
* **Rust side**: `sqliters_types::dtrace!` at the same decision points (compiled only with `--cfg sqliters_dtrace`).
* **Differ** `h1/trdel.py`: the part of a scenario before `-- @run` is executed once by the plain C shell; the file is copied; the delete-heavy part after the marker is run on one copy by the instrumented C shell and on the other by the Rust trace build. So the tree ENTERING the deletes is identical, whatever the insert side of the Rust engine would have built (insert-side splits are step H2, index bulk fill H3). Compared: the `ctx=del` event lists (event by event, all fields), stdout, `PRAGMA integrity_check` of both files by both engines, `page_count`, `freelist_count`, and the per-page shape C's `dbstat` reports (path, page number, kind, cell count, payload, unused bytes).
* Events: `del` (trigger test: page, nFree, usableSize, outcome), `delint` (interior cell replaced by its predecessor: page, cell index, leaf, size, fits/overflow), `delup` (second `balance()` at the interior page), `step` (one per `balance()` loop iteration: page, overflow cells, nFree, outcome), `sib` (parent, iParentIdx, nxDiv, nOld, bBulk, old siblings as page:cells:nFree), `dist` (k, leafData, cell count, cntNew[], szNew[]), `pages` (page numbers of the new sibling set after the renumbering sort, pages freed), `div` (each divider: left page, size, key — rowid or FNV-1a of the cell — fits/overflow), `edit` (page, cells, nFree, editPage/rebuildPage), `shallow`, `deeper`, `quick`.

Mismatches and their cause:
* `c_idxscan_1024` — every tree sees the same decisions in the same order (per-tree streams identical, final files identical in shape and page numbers); the ORDER BETWEEN TREES differs: for a one-pass DELETE driven by an index scan C deletes the table row first and the entry of the scan index last (`sqlite3GenerateRowDelete`: `iIdxNoSeek`), this engine deletes all index entries first. Engine-level (known gap of step 5g, class B9), not a b-tree decision.
* `c_trigger_1024` — a difference that exists in `step5j_bin` as well and is not caused by this step: `DELETE … WHERE k<500` with an `AFTER DELETE` trigger that deletes another row of the same table. C collects the rowids in a RowSet and visits them in rowid order; this engine visits them in index order, so the trigger removes different rows (C leaves 1497 rows, Rust 1377). Minimal: `CREATE TABLE t(id INTEGER PRIMARY KEY,k INT); CREATE INDEX tk ON t(k); INSERT INTO t VALUES(1,2),(2,1),(3,9); CREATE TRIGGER tr AFTER DELETE ON t BEGIN DELETE FROM t WHERE id=old.id+1; END; DELETE FROM t WHERE k<5; SELECT id FROM t;` → C `3`, Rust nothing.

## 3. Coverage gaps (c): outcomes never exercised = not verified

* `balance_quick` (B4) and every `bBulk=1` branch (N1 `nxDiv=i-2+bBulk`, N8, N9 `nearby=1`): reachable only from inserts; the code is ported and compiled, the insert side does not call it before step H2. C exercised them only with `ctx=ins`.
* `anotherValidCursor` → `SQLITE_CORRUPT` (B2), page reference count check (B3, not ported), sibling type mismatch / empty sibling / more than five siblings (N4, N7): corrupt databases only; no scenario.
* k=5 new siblings and two allocations in one `balance_nonroot` during a delete: not reached by any scenario (C neither).
* `bPreserve` (D2): no counterpart; only its visible effect (results of scan-driven deletes) is compared.
* In-page placement (P1): not traced; it decides bytes inside a page, not shapes.
* Trees built by the Rust insert side differ from C's before the first delete (H2, H3): for those, decisions were compared only through the divergence finder (layers), not event by event.
